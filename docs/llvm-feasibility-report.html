§1

What SpecForge actually compiles

The project’s own README states the thesis that decides this entire question: “SpecForge is not a code generator and not a test runner.”[E1] “The graph is the product.”[E2] Every output the compiler produces is data consumed by agents and tools — JSON, DOT, Mermaid, DBML, markdown. Nothing is executed.

Scale, measured: 102,593 lines of Rust across 17 crates + integrations (largest: emitter 16,460 · cli 15,960 · wasm 15,866 · registry 14,987).[E3] The graph engine is a deliberate hand-rolled HashMap<Node> + Vec<Edge> with source/target indexes — petgraph 0.8.3 sits declared in Cargo.toml:46 with zero usages in crates/.[E4] That is the project’s dependency culture in one fact: even a mature, pure-Rust graph library was set aside to keep the core exactly as big as the mission (RES-26, zero-entity core[E6]).

§2

What LLVM is for

LLVM is a machine-code factory. Its entire value concentrates in phases SpecForge does not have: instruction selection, register allocation, instruction scheduling, ABI handling, target descriptions. Its cost concentrates in everything else.

§3

The fit gap, capability by capability

Each LLVM capability is checked against each SpecForge pipeline need. The pattern is uniform: the need already has an owner; LLVM would be a second implementation of something already solved.

Register allocationMap values to physical registers✗No registers exist in a JSON graph

Target triples / ABIsPer-architecture calling conventions✗One “target”: JSON Schema draft 2020-12[E3]

The one-line fit test

LLVM answers: “how do I turn an intermediate representation into fast machine code?” SpecForge’s question is: “how do I turn prose into a validated, typed graph that agents can query in a few KB?”[E2] Different problem, disjoint solution space.

§4

The option space

“LLVM” is really four different decisions bundled together. Separating them changes the answer for each.

OPTION A

Status quo — emit data

KEEP

The pipeline already parses, resolves, validates, and emits 7 formats[E3]. Adding LLVM would add 0 capabilities and 1 toolchain.

  • Deliverable fit: 10/10 — every stated feature maps to data emission
  • Marginal LLVM value: none identified across all 9 capability rows of §3
NO ACTION
OPTION B

LLVM full integration

REJECT

llvm-sys/inkwell behind the emitter: version-locked per LLVM release[E20], system-LLVM provisioning per platform[E25], GB-scale build artifacts[E13] — to produce machine code nothing can run.

  • Contradicts the dependency grain: petgraph was already declined[E4]
  • Contradicts roadmap targets: CLI <50ms extension load via Cranelift AOT[E10]
AVOID
OPTION C

MLIR as the IR story

PREMATURE

MLIR’s dialect-and-progressive-lowering model[E24] pays off when a compiler needs multiple semantics-bearing levels. SpecForge has one IR — the typed graph — and one serialization target. A C++ toolchain for a Rust workspace buys a second IR to keep in sync with the first.

REVISIT ONLY IF executable model semantics ever exist
OPTION D

Cranelift native codegen

DORMANT

If validation rules ever become a hot loop worth compiling (the Pydantic-v2 move[E9]), Cranelift is the tool: it is already in Cargo.lock (0.128.4 via wasmtime)[E5], compiles ~40% faster than LLVM[E16], and trades only peak throughput[E19] — which validators do not need.

KEEP AS CONTINGENCY — NO WORK NOW
OPTION F

Z3 via SMT-LIB (the prover)

ADOPT — FOR RES-25 ONLY

The correct “heavy tool” for analyze --prove[E7]. Predicates over a graph lower cleanly to SMT-LIB; Z3 is the field’s standard engine (13,345+ citations)[E23] and Dafny ships exactly this chain[E22]. Pure-Rust sibling: the z3-sys/SMT-LIB-text route avoids C++ build complexity in CI.

SPIKE §9-A BEFORE RES-25 PHASE 1
OPTION H

KLEE on LLVM IR (the prover, LLVM edition)

REJECT

KLEE symbolically executes LLVM bitcode of compiled programs[E21]. SpecForge conditions have no program semantics — you would have to invent semantics, synthesize a harness, compile it, then let KLEE discharge constraints with… an SMT solver[E21]. Two lossy hops to arrive where Option F starts. Full analysis in §7.

AVOID

§7

Prover deep-dive: where LLVM nearly — but doesn’t — belong

This is the honest steelman. If LLVM enters SpecForge anywhere, it enters through specforge analyze --prove[E7] via KLEE. Here is why that path is structurally worse than the direct one, with the evidence.

The three decisive facts

1 · KLEE’s input contract excludes SpecForge’s artifacts. KLEE symbolically executes LLVM bitcode — it requires a compiled program with a C-compatible ABI[E21]. A behavior.requires clause is a predicate over graph nodes; there is no bitcode of it and no honest way to manufacture one without first deciding its executable semantics — which is precisely the thing SpecForge deliberately does not have (it is a spec language, not a programming language[E1]).

2 · Symbolic execution bottoms out in SMT anyway. KLEE’s engine discharges accumulated path constraints with an SMT solver[E21]. For closed, quantifier-light predicates — exactly what requires/ensures over typed fields are — direct SMT-LIB lowering reaches the same solver with fewer lossy translations. The field’s reference verifiers (Dafny/Boogie[E22], the B-Method’s provers[E9]) confirm the pattern at industrial scale.

3 · The architecture already reserves the right hook point. The extension protocol declares compiler passes with descriptors (condition_check, phase analysis)[E6], and RES-25 routes all formal analysis through @specforge/software Wasm validators, not core passes[E8]. A Z3-backed pass slots into the designed seam; an LLVM toolchain does not — it would sit under the host, not in the extension model, changing deployment for every user who never asked for a prover.

Where LLVM-based checking IS the right tool — and why it is out of boundary

Verifying the implementations agents write from specs (the consuming side) would legitimately use KLEE/LLVM on that generated code. But SpecForge’s contract with implementations is the trace protocol: verify kinds, specforge collect, testing-as-oracle[E1]. Checking binaries is the consumer’s CI problem, not the spec compiler’s.

§9

Recommendation and the spikes that prove it

Recommendation

1 · Do not adopt LLVM anywhere in the core. The pipeline emits data; LLVM manufactures machine code[E1]. Rejected on fit (§3), cost (§8), and culture (§1 — petgraph precedent[E4]).

2 · For analyze --prove, lower to SMT-LIB and call Z3 through the extension-pass seam that already exists[E6]. Keep Boogie-style VC generation as the escalation path if naive lowering stalls.

3 · Record Cranelift as the designated native-codegen contingency. It is already in the dependency tree[E5]; any future “compile the validators” idea benchmarks it first, not LLVM[E16].

4 · Archive this decision as a governance decision entity so the question stays answered[E6].
