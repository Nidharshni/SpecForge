CONTEXT

What SpecForge actually does

You describe intent in .spec files. A compiler turns them into a typed graph, checks that every reference resolves, and rejects orphans and cycles. Agents read that graph through exports or MCP. Separately, your tests declare which obligations they prove, and specforge collect runs them to record what is proven.

Infos · what is genuinely good

The parts worth keeping

I001 · info

Verified traceability is a real moat

Most "spec for agents" tools stop when the code is generated. SpecForge keeps going. A requirement links to a verify obligation, a test names that obligation, and collect only marks it proven when the test passes. That answers a question teams ask constantly and usually cannot answer: which requirement does this test prove, and does it actually pass?

I002 · info

Your audit is the best pitch you have

In September you judged every test linked with #[specforge_test]. Agents had written most of them. More than a third claimed a proof they did not deliver. SpecForge made the claims explicit enough to check, which is how you found them. No marketing line in business/ is as convincing as this chart.

I003 · info

The architecture is right

No domain words in the core

The compiler only knows keyword name { fields }, references, orphans and cycles. Every entity kind comes from an extension. If a new domain needed a compiler change, the design would have failed, and so far it has not.

It runs on itself

185 .spec files describe SpecForge, gated in CI, served over MCP and LSP. Forty ADRs record the decisions. This is a working tool, not a slide deck.

Errors · these sink it if left alone

Why it could flop

E101 · error

The headline number has never been measured

The README promises that first-attempt accuracy rises from about 30% to 70–85% with the graph. The business plan adds "75–86% fewer tokens". The eval harness exists, and its own README says Status: Unrecorded. The pitch, the projections and the roadmap all rest on a number nobody has produced.

Unsourced statistics

business/01-executive-summary.md cites "Anthropic Usage Data: Claude Code users spend 67% of context on file reading". I know of no published source for this. If you cannot cite it, delete it. One skeptic who checks it will stop trusting the rest.

The fix is cheap

tasks.json holds 10 tasks. Grow it to about 50, run each with and without the graph on one fixed model, and publish the result either way. A modest real number such as 45% → 60% beats every claim in the repo.

E102 · error

Built far ahead of anyone asking for it

Agents make building cheap, which makes it easy to keep building instead of asking whether anyone wants the thing. SpecForge has a WASM extension runtime, a registry server, Z3 proofs, two MCP protocol versions, an LSP and a ten-part business plan. It has 15 GitHub stars, a release candidate from 1 October, and no outside users I could find.

Warnings · each one slows adoption

Friction that compounds

W201 · warning

Writing the spec costs more than writing the code

The todo-app example needs 309 lines of spec and 30 entities of 18 kinds to describe three behaviors. In the repo itself, 42,231 lines of spec sit beside the Rust (18% of its size), and that spec had drifted to 481 warnings at the root before a cleanup pass. If the author, with a fleet of agents, struggles to keep it in sync, a normal team will not manage. Spec drift is what killed UML, model-driven engineering and Cucumber at scale.

W202 · warning

A new language in a world where agents speak Markdown

Here is the same requirement written both ways. The DSL gives you something real: the compiler rejects task_created if no such event exists. It also costs something real. This repo ships 18 specforge-* skills so that agents can write the format at all.

The way out is to make the syntax something nobody types. Agents and people edit entities through typed operations, SpecForge writes the .spec text, and anyone who wants Markdown gets a generated export. That is proposal P301 below.

W203 · warning

The competition is missing from the strategy

I searched business/, vision/, docs/ and spec/. None of them mentions GitHub Spec Kit, Kiro, Tessl or OpenSpec, which are the real "specs for agents" products and have far more distribution. Placed on a map, they cluster in one corner. SpecForge's open space is the opposite corner.

W204 · warning

The token-savings argument weakens with every model

"Agents waste tokens rediscovering intent" was a strong pitch when context was small and search was clumsy. Each model release brings longer context and better code search, so saved tokens are worth less every year. Proof that the code matches intent does not lose value that way. It becomes more valuable as agents write more of the code.

Proposal · P301

Nobody writes .spec by hand

P301 · proposal

The idea: people and agents fill in fields, and SpecForge creates, updates and deletes the .spec text itself. Anyone who wants to read the spec gets a Markdown export. Nobody learns the syntax.

My take: this is the right direction, and most of the hard part already exists. I would change the order of the work, and there is one trap to avoid. The .spec file stops being something people write and becomes a storage format they review in pull requests. Keep it as text, because readable diffs are worth keeping. Just stop asking anyone to type it.

The forms are designed

prototype/web/ already builds its forms and previews from the extension schema, with nothing hard-coded per entity kind. That was the hard design problem.

Edits have a pattern

rename, format and migrate already change .spec files, and ADR 0022 says a mutation reports what it wrote.

Edits can be lossless

ADR 0038 gives one lexer and one syntax tree. An edit can change one field and leave comments and layout untouched instead of rewriting the file.

The rule that makes it trustworthy: validate before writing

Every edit is applied in memory and compiled first. It reaches disk only if it adds no new errors. That gives you a guarantee you can put in the README: an edit can never leave the spec broken.

The trap: forms remove the syntax, not the workload

The todo-app still needs 30 entities of 18 kinds for 3 behaviors, whether they are typed or filled in. A form with dozens of fields turns into Jira, and people hate filling in Jira.

What forms fix: W202

Nobody learns a new language. The 18 specforge-* authoring skills become unnecessary because agents call typed tools instead of writing text.

What they don't fix: W201

Someone still has to decide and maintain all those entities. That cost only drops when agents fill the forms and people approve the result.

The hard parts

Where entities go

Which file a new entity lands in, and keeping use imports current. Pick one rule, such as one file per kind per feature, and let the formatter enforce it.

Comments and order

Every edit must keep comments and ordering. The syntax tree makes this possible. Round-trip tests that edit a file and compare the result make it certain.

Concurrent edits

An agent, a person in the UI and two git branches can touch one file. Small local edits keep merge conflicts rare. Regenerating whole files would make them constant.

Build order

The web UI comes last. Building a full editor now would repeat E102: more infrastructure before anyone outside has used the product.

Proposal · P302

An operating system for hard skills

P302 · proposal

Your framing: today's agent skills are soft skills. They are instructions an AI reads in its context window and tries to follow. SpecForge holds hard skills: vocabulary, structure, rules and measurements written as code, which work the same way every time. So SpecForge is not only for software. Anything with structure and rules can have a hard skill, from a report to a regulatory dossier.

My take: this is a sharper thesis than "context for agents", and I would lead with it. A soft skill tells an AI how to do the work. A hard skill decides whether the work is acceptable. In one line: you can validate a rule, but you cannot validate a prompt. It also answers W204, because hard skills do not depend on how big context windows get.

The trust boundary

In critical work, AI is useful but cannot be the last word. SpecForge sits between the AI and the person who signs. The AI may only change the spec through typed edits (P301). The hard skill checks everything it changed. A person reviews what the hard skill flags and signs.

Regulators are drawing the same line

Generative AI is being kept out of critical GMP decisions

The draft EU GMP Annex 22 on artificial intelligence, published for consultation in July 2025, limits critical GMP uses to static models with deterministic output. It keeps generative models and LLMs out of critical applications and expects a qualified person in the loop elsewhere. FDA's January 2025 draft guidance on AI in regulatory decision-making asks for a risk-based credibility assessment of each model. Both point to the same design: AI drafts, deterministic checks decide, people sign. Check the current status of both texts before quoting them to a customer.

Worked example: your report idea, as an annual Product Quality Review

EU GMP Chapter 1, section 1.10 lists twelve things every yearly Product Quality Review must cover. That list becomes a hard skill: twelve required sections, each with the data, trend and conclusion it needs, and rules that check the data. The AI writes the trend commentary. The hard skill measures completeness and blocks the report while anything required is missing.

Proposal · P303 · the capstone

Releasing one biologic batch

P303 · the fruit of the product

One signature. Twelve hard skills. Every fact proven.

Before any batch of medicine reaches patients in the European Union, a Qualified Person (QP) must personally certify it. The QP signs that the batch was made and tested exactly as registered and under good manufacturing practice. To do that, they need facts from manufacturing, the laboratory, quality, regulatory, suppliers, logistics, training and IT, and every one of them must be right. This is where all the hard skills on this page meet. It is the strongest example of what SpecForge is for.

1legal signature, by a named person
12hard-skill extensions combined
150rules checked on every change
1,184records in the batch's graph

The product, batch, records and numbers in this section are an illustrative scenario. The regulations and real-world events cited are real, and listed with sources at the end.

Why this is the hardest thing to control

Batch certification is the point where every earlier mistake becomes the QP's problem. Three things make it hard.

It is personal and legal

EU law (Directive 2001/83/EC, Article 51) makes the QP personally responsible for each certified batch. A wrong signature can mean a recall, harm to patients and action against the QP.

The facts live in six systems

Manufacturing records sit in the MES, test results in the LIMS, deviations and changes in the QMS, registrations in the RIM, training in the LMS and shipments in logistics. No single system sees the whole batch.

It runs against the clock

A sterility test needs at least 14 days of incubation. Environmental samples take days to read. Investigations open and close while the batch waits, and each one can change the answer.

      When this goes wrong in the real world

      Each of these failures crossed system or company boundaries, and a hard skill in this stack targets that kind of failure.

      Heparin, 2007–2008

      Heparin active ingredient contaminated with oversulfated chondroitin sulfate entered the US supply through its supply chain. Patients had severe allergic reactions and deaths were reported. Recalls followed and the pharmacopoeia tests were changed. Targeted by: @pharma/suppliers, duty 9.

      Valsartan, 2018

      A manufacturing process change at an active ingredient maker created NDMA, a probable human carcinogen. It went unnoticed for years and led to worldwide recalls. Regulators then required nitrosamine risk reviews for all medicines. Targeted by: @pharma/change-control and @pharma/impurities, duties 6 and 9.

      Ranbaxy, 2013

      The company pleaded guilty in the United States to felony charges over adulterated drugs and false statements about its data, and agreed to pay 500 million dollars. Targeted by: fingerprinted evidence trails and the Part 11 controls SpecForge still needs.

      FDA inspection data, every year

      Failure to thoroughly investigate unexplained discrepancies (21 CFR 211.192) appears every year among the most cited drug manufacturing observations in FDA's published inspection data. Targeted by: @pharma/deviation, duties 5 and 7.

      What this does not do

      It does not decide. The QP decides and signs. SpecForge shows what is proven, what is not, and the evidence behind each.

      It only sees what is imported. Every fact here comes from the MES, LIMS, QMS, RIM, LMS or logistics. Import connectors do not exist yet.

      Rules can be wrong. Each extension is GxP software. It must be validated, owned by QA, and changed only under change control.

      It lacks Part 11 controls today. Signatures with meaning and a per-record audit trail must be built before any GxP use. The design is in P304, Signatures and the audit trail.

      Proposal · P304 · the second capstone

      A software factory for critical software

      P304 · spec → plan → implement → review → security → safety → comply

      Software where a bug can hurt someone, built by agents, proven by hard skills.

      Insulin pumps, braking systems, flight controls and pharmaceutical systems are all governed by software standards. Each standard demands the same thing in different words: every requirement traced to its design, code and tests, every change assessed, every risk controlled, and evidence for all of it. Today teams pay for this with heavy tools and months of document work. This proposal is a set of SpecForge extensions that turns those standards into hard skills, so AI agents can do the drafting and the factory proves the result on every change.

      None of these @factory/* extensions exist yet. The design draws on research into GitHub Spec Kit, GSD, Agent OS and Siemens Polarion ALM, on the qadi spec and the SpecForge planning documents, and on Bridger's assessment of SpecForge. The product GlucoPilot and its records are an illustrative example.

      The real gap: an expert toolkit

      Bridger's sharpest point is that SpecForge has a checker but no toolkit for the experts who must write the standards. A quality engineer who knows Part 11 cannot write Rust compiled to WebAssembly. The assessment lists eight gaps. Each one is a precondition for the factory.

      GapWhat the expert needsWhy the factory depends on it

      Design decisions the factory adopts from Bridger

      • Kebab-case IDs per kind. Each kind declares an ID pattern, so BEH-BR-041 is a real identifier and not an alias. Bridger rated this gap hard: today's identifier pattern rejects hyphens.
      • Addressable requirement statements. One behavior holds several MUST statements, each with its own address such as BEH-BR-041.r1. Coverage is then tracked per statement, not per behavior.
      • Prose stored verbatim. Prose is about two thirds of Bridger's content, and only 18% of its requirement blocks would survive re-wrapping. The factory stores prose exactly and renders Markdown byte for byte, with render --check to catch drift.
      • Only executed tests are evidence. Every evidence record keeps versions, lockfile hash, environment, executor and raw log. Prototype findings are marked as not evidence. Claims are graded verified, executed or inferred.
      • A library supports; only the regulated system satisfies. Mapping edges to a regulation use different verbs, and the factory checks which kind of entity may use each.
      • Status honesty. A document cannot be Effective, and a decision cannot be Accepted, while its implementation is absent. Agent reviews are recorded as agent reviews, never as independent human reviews.
      • Waivers that expire. An exception names one rule code, a reason, an approver and an end date. After the end date the rule applies again.

      The factory floor

      Seven stages, each held by hard-skill extensions, with a gate between stages. A gate is a set of rules that must pass before work moves on. Agents draft in every stage through typed edits. People approve at the gates that need judgement. The profile runs underneath and decides which rules each gate applies.

        GAP · 21 CFR Part 11 · EU Annex 11

        Signatures and the audit trail

        Regulated work runs on signatures. A QA lead approves a release, a reviewer approves a change, a QP certifies a batch. Part 11 and Annex 11 say that when those signatures are electronic, the system must prove who signed, what they meant, when, and that the signed record has not changed since. The system must also keep an audit trail that nobody can quietly rewrite. Today SpecForge cannot prove any of that.

        Status, stated plainly

        Until the signing service exists, factory approvals are evidence of intent, not electronic signatures.

        Every approval, signoff and review in the factory today is a record that someone typed. It names a signer, but nothing proves that person signed. Do not use factory approvals as GxP records, and do not present them to an auditor as Part 11 signatures, until the design below is built and validated.

        Covered: signatures as a requirement on the product

        @factory/gxp checks that a pharma system you build declares its electronic records, audit trails and signature points, and that each signature shows name, date, time and meaning (rules GXP-02 and GXP-03). That is about the software being built.

        Missing: signatures on the factory's own records

        When the factory itself records an approval, the signer is free text in a .spec file. An agent could type it. Git dates are set by the client and history can be rewritten. This is about the factory, and it is the gap this section closes.

        A sealed trail, and what tampering looks like

        Each trail entry stores the hash of the entry before it, so the entries form a chain. A seal stores the hash of the last entry and is anchored outside the repository. Pick a scenario to see what the compiler reports.

        
    
        

    
        
      
        What has to be built
        
      
        
        
        1. The extension
        @factory/signatures adds signer identities, single-use tickets, signatures, trail entries and seals, with rules SIG-01 to SIG-07. It is in the catalog below. Most of it is ordinary compiler work.
        
        
        2. A signing service
        A small service, for example specforge sign backed by a trail store, that checks identity through SSO with a second factor, stamps trusted time and appends to the sealed trail. A compiler cannot do this alone, because it needs identity, a clock and storage that shows tampering.
        
        
        3. Its validation
        The signing service is GxP software itself. It needs requirements, a risk assessment and executed tests, which the factory can produce for it. Until then the status note above applies.

        What the factory must not claim
        
      
        It does not certify anything. Notified bodies, the FDA, certification authorities and inspectors decide. The factory produces evidence and shows gaps.
        
      
        It is itself a tool to qualify. Under DO-330 and ISO 26262-8, a tool whose output replaces a verification step needs qualification. That applies to SpecForge and to every AI model the factory uses. The @factory/tools extension records this, and the qualification itself is real work.
        
      
        Rules encode one reading of a standard. A wrong rule gives false confidence. Each rule needs an owner, a rationale and a test.

    Why this is the second fruit
    
        Agents write critical software. Hard skills prove every line of it traces to a reason, a test and a signature.
        
    
        Spec Kit, GSD and Agent OS showed that agents work better with specs, plans and standards. Polarion showed what regulated teams must prove. The factory joins the two: agent speed with compiler-checked evidence. If one regulated team ships one release with it and passes its audit, SpecForge has a second market.
