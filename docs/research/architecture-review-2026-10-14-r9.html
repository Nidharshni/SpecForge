Problem. Four mechanisms try to name a refusal's argument: the table, a string match on the code, call-site with_argument calls, and TargetError. None of them sees every code. In a debug build a missed code panics; in a release build the reply has no argument.

Solution. The operation's refusal carries a typed request field as its subject. Each tool maps its request's fields to its argument names once, exhaustively.

add_extension {"specifiers":["git+https://example.com/x"]} → -32603 Internal error   (E064, panic tool.rs:521)
remove_extension {"name":"@@bad"}                          → -32603                  (E072)
add_extension {"specifiers":["./notwasm.txt"]}             → -32603                  (E028)
  • Locality: a new ops refusal needs no MCP edit
  • Leverage: prompts and trace use the same rule
  • Delete the table, the match and the panic
  • One test per request type
⚠ Contradicts ADR 0033's round-8 amendment, which chose the table and merged today. It is worth reopening because the table already misses five codes on the add, remove and plan paths. The ADR's "an operation writes no argument name" still holds, since the subject is a request field, not a surface's spelling.
