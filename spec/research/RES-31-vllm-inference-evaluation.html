SpecForge Research Dossier · RES-31 · 2026-09-23

Can vLLM be a better option for SpecForge?

Short answer: yes — but never inside the compiler. vLLM is evaluated here against the two places where LLM inference can legitimately touch this project: the EmbeddingProvider outbound port, and the consumer side of the specforge infer workflow. EXHIBIT SET 01 · REPO-GROUNDED

Where could inference possibly live in a deterministic compiler?

SpecForge's core claim is that it is "deterministic infrastructure — not an AI agent itself" [E17.2]. The compiler parses, resolves, validates and exports a typed graph; every AI behavior lives outside it. Any vLLM evaluation must therefore start from the architecture, not from the engine's feature list.

EXHIBIT 01SpecForge architecture with candidate vLLM integration surfacesevidence: README.md · crates/ tree · spec/extensions/embeddings/ports.spec#8F40 · spec/features/infer.spec#68D3
Reading: the compiler (left, solid) is closed to inference by design. S1 and S2 (dashed amber) are the only architecturally legal integration points for a serving engine. Everything on the right is external infrastructure that consumes SpecForge — vLLM included. [E17.1–E17.5]

SECTION 03 · TECHNOLOGY EVIDENCE

What vLLM actually is, on the record

vLLM is a PyTorch Foundation project for high-throughput, memory-efficient LLM serving [E16]. Five properties matter for this evaluation; each is charted or cited below.

EXHIBIT 02Serving throughput — the founding claim, still the headlineevidence: vllm.ai (2023) [E1] · arXiv 2511 perf study (2025) [E18]
PagedAttention treats the KV cache like OS pages — near-zero waste vs contiguous pre-allocation — which is why throughput scales with concurrency instead of collapsing. The 2023 blog figures [E1] were independently reproduced up to 24× vs TGI under high-concurrency load in a Nov 2025 arXiv performance study [E18].
EXHIBIT 03Concurrency is the real differentiator — 2026 independent measurementsevidence: Ay 2026 MDPI [E8] · RunPod 06/2026 [E4] · Jarvis Labs 05/2026 [E5] · Ollama docs [E9] · Ginger Labs [E10]
Honest reading: vLLM is not the fastest engine in 2026 — SGLang leads high-concurrency throughput by ~30% on some workloads [E4][E5], while vLLM leads TensorRT-LLM by ~11% on B200 agentic coding [E6] and batch jobs by 15–20% [E7]. vLLM's edge is breadth + stability: widest model/hardware support [E16], xgrammar structured outputs as default backend [E3], pooling/embeddings API [E15], and 100% success rate under 100-way concurrency vs Ollama's sharp degradation [E8]. For a port-adapter (S1) that's exactly what you want: boring, broad, stable.

The five properties that matter for SpecForge

PropertyMechanismRelevance to SpecForge
Continuous batching + PagedAttention [E1]Requests join/leave every decode step; KV memory paged per-block → GPU stays saturated at high concurrency.specforge infer across a monorepo = thousands of independent file-analysis tasks → ideal batch shape (§06).

SECTION 05 · INTEGRATION SURFACE S1

EmbeddingProvider → vLLM: legal, cheap, and rarely necessary

The embeddings extension already specifies the seam: an outbound port with generateEmbeddings(texts) → float[][] and computeSimilarity(...), abstracting "OpenAI, local model, etc." [E17.1, E17.4]. vLLM serves pooling models on the same wire format [E15]. The concept proof is therefore trivial — it's an HTTP client.

EXHIBIT 04S1 sequence — embed + semantic query, cache-firstevidence: behaviors.spec#4320 · docs.vllm.ai [E15]
The caching and E028 semantics are already in the behavior contracts [E17.4]; the adapter only fills the port. Wire format is OpenAI-compatible, so the same adapter serves vLLM, SGLang, Ollama or LM Studio — principle §6 respected.

But the economics say: this surface alone never justifies a GPU

QuantityValueBasis
Typical validated graph (this repo, 4 extensions)≈2,000 entities[A6] order-of-magnitude
Embedding text per entity (contract + title + relations)≈250 tokens[A6]
Full re-embed volume0.5M tokens= 2000×250
Cost via managed API (text-embedding-3-small class)$0.01[A6]
Time on 1×H100 vLLM embedding endpoint≈10s[A6] ~50K tok/s
S1 verdict
Implement the adapter because the port exists and enterprise adopters will demand an on-prem embeddings path for private graphs — not because of throughput or price. At single-project scale the API is 1¢ and a local model via Ollama is equally fine. vLLM earns its keep on S1 only when one GPU host serves many projects/teams (org-wide semantic search) — then continuous batching over pooled requests is exactly its strength. Also note: single-user TTFT is the one axis where Ollama beats everything (45ms) [E10] — fine for the zero-config default path.

SECTION 06 · INTEGRATION SURFACE S2

Self-hosted infer batch: where vLLM's throughput actually cashes out

specforge infer is an agentic workflow: an AI agent walks source files, emits entities, records progress in specforge-infer.json, resumable by content hash [E17.5]. The model driving that agent is external to SpecForge by design — but teams choosing where that model runs face a real decision: managed API vs self-hosted serving. For private codebases, the egress argument alone can decide; the TCO below quantifies the rest.

EXHIBIT 05Monthly cost vs infer volume — managed APIs vs self-hosted vLLM (log scale)evidence: pricing E11–E13 · task shape A1 · task costs computed, not estimated
Honest reading: against frontier-API pricing, self-hosted vLLM breaks even at ~3.1–5.0K infer tasks/month on a burst schedule — an active team inferring a monorepo, or a consultancy batching client repos. Against Chinese-frontier API pricing (DeepSeek/Qwen) self-hosting never wins on cost within plausible volumes — there the decision is SEC-1 (data egress), full stop. Capacity is a non-issue: one H100 clears a 10K-task month in ~37 GPU-hours [A3].

SECTION 07 · FLAGSHIP CONCEPT PROOF

Publish the grammar, guarantee the syntax: .spec via constrained decoding

This is the highest-leverage vLLM-related move available to SpecForge — and it costs zero GPU hours. The tree-sitter grammar [E17.6] shows the DSL is deliberately tiny: four dedicated constructs plus one generic entity block. That grammar can be transcribed once into a GBNF/EBNF artifact and shipped with the extension. Any vLLM-backed agent then passes it as structured_outputs.grammar [E3] — and the sampler mathematically cannot emit a token sequence that violates it. RES-29 already established extension-defined grammars for parsing; this is the mirror image for generation.

EXHIBIT 06The infer loop with grammar-constrained decoding — retry loop deletedevidence: docs.vllm.ai [E3] · grammar.js#C5E2 [E17.6] · infer features [E17.5]
Impact model, tied to the repo's own economics research: RES-18 documents the rework spiral — chained 90%-accurate calls collapse to 59% accuracy (0.9⁵) and agents burn 40–60% of tokens on exploration/discovery [E14]. A syntax-retry round trip per malformed file is one of the cheapest failures to delete: grammar constraints do it deterministically, at zero marginal GPU cost (token masking adds negligible latency [A7]).

Concept proof — core-DSL GBNF sketch

Mirror of grammar.js#C5E2 (generation side). Simplifications marked; the shipped artifact would be generated from the grammar plus per-kind field constraints from extension manifests — strictly tighter than tree-sitter.

# specforge-core.gbnf — generation-side grammar (sketch)
# source: crates/kernel/tree-sitter/grammar.js
root      ::= block*
block     ::= useLine | entityBlock | unionBlock
            | specBlock | defineBlock | verifyLine

useLine   ::= "use" ws+ useTarget NL
useTarget ::= str
            | "{" binding ("," ws binding)* "}" "from" str
            | "*" "as" ident "from" str
binding   ::= ident ("as" ident)?

# generic entity block: ANY keyword accepted (core has zero domain)
entityBlock ::= ident ws+ ident (ws+ str)? ws* "{" NL
                (field | verifyLine)* "}" NL
specBlock   ::= "spec" ws+ str ws* "{" NL (field|verifyLine)* "}" NL
defineBlock ::= "define" ws+ ident ws* "{" NL field* "}" NL
unionBlock  ::= ident ws+ ident "=" ws* variant ("|" variant)* NL
variant     ::= str | "-"? int | ident

field     ::= ws* ident ws+ value annotation* NL
verifyLine ::= ws* "verify" (ws+ ident)? ws+ str NL
annotation ::= "@" ident str?
value     ::= tqs | str | date | "-"? int | bool
            | list | nested | arrayType | ident
list      ::= "[" (item ("," item)* ","?)? "]"
item      ::= str | refId | int | ident
nested    ::= "{" NL field* "}" NL
arrayType ::= ident "[]"
refId     ::= ident "." ident ":" refTail
refTail   ::= [^ \t\n"{}()\[\],]+
date      ::= int "-" int "-" int
str       ::= "\"" [^"\\\n]* "\""
tqs       ::= "\"\"\"" tqsBody "\"\"\""  # simplified; escapes per grammar.js
ident     ::= [a-zA-Z_] [a-zA-Z0-9_]*
int       ::= [0-9]+
bool      ::= "true" | "false"
ws        ::= [ \t] | NL
NL        ::= "\n"

Integration — one extra request field

# server: any vLLM ≥0.12 deployment
$ vllm serve Qwen/Qwen3-Coder-30B-FP8 \
    --structured-outputs-config.backend xgrammar

# agent: pass the extension-shipped grammar
from openai import OpenAI
client = OpenAI(base_url="http://gpu.internal:8000/v1",
                api_key="-")
r = client.chat.completions.create(
  model="qwen3-coder-30b",
  messages=[
    {"role": "system", "content": preamble},   # graph context [E14]
    {"role": "user",  "content": src_file},
  ],
  extra_body={"structured_outputs": {
    "grammar": open("specforge-core.gbnf").read(),
  }},
)
# r.choices[0].message.content → parses. always. [E3]
$ specforge check   # semantic gate: refs, orphans, cycles
Why this is the flagship
It converts SpecForge from a validator of agent output into a constraint provider for agent decoding — strengthening the Graph Protocol ecosystem (principle §6) at artifact cost only: one grammar file per extension, generated from sources of truth that already exist [E17.6][E17.7]. Works with any xgrammar/llguidance-backed server: vLLM, SGLang — not just one vendor.

SECTION 10 · RISKS, COUNTER-EVIDENCE, FALSIFIERS

What would make this verdict wrong

Risk / counter-evidenceSeverityMitigation / tripwire
SGLang is faster at high concurrency (~16.2K vs ~12.5K tok/s; 61–63ms vs ~70ms decode) [E4][E5]MEDIUMAll S1/S2 artifacts target the OpenAI wire format and portable grammars (GBNF/EBNF both supported by SGLang) — engine swap is config, not code. Re-benchmark quarterly.
Grammar constraints can distort model quality — masked tokens may degrade reasoning on hard files [A7]MEDIUMGate P1 on measured entity-acceptance rate vs unconstrained baseline, not just parse validity; keep grammar optional per-request.
GPU ops burden — CUDA versions, weights, VRAM; zero-config principle tension [E16]MEDIUMP3 is docs-only; nothing enters the binary. Teams without GPU ops simply stay on APIs (matrix says they should).
API price floors keep falling (Qwen Flash $0.03/$0.13 today) [E13] — cost case for self-host erodesMEDIUMVerdict already rests on SEC-1 (privacy) + STR-1 (grammar) + batch stability, not on cost. Refresh ECO-1 table every quarter.
macOS story — this machine is Apple Silicon; vLLM-on-Mac is a community port (vllm-metal), not first-class [E16]LOWLocal-dev path documented as Ollama/llama.cpp (both GBNF-capable); vLLM positioned as team/server infrastructure.
vLLM API churn — guided_* fields already deprecated in v0.12 for structured_outputs [E3]LOWAdapter pins documented request shape in one module; integration tests catch drift.
Falsifiers — what new evidence should reopen this decision
(1) SGLang or successor ships clearly better grammar-fidelity + embeddings support → re-run matrix, swap engine under the same port. (2) vllm-metal reaches first-class status → single-machine story changes for every Apple-Silicon developer. (3) Frontier APIs add arbitrary-CFG constrained decoding server-side → P1's differentiator narrows to self-host only. (4) Measured STR-1 entity-acceptance < unconstrained baseline → demote grammar recipe from recommended to experimental.
