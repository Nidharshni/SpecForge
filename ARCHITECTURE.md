# Architecture

How SpecForge is built. For what it is and why it exists, start with the [README](README.md).

## Zero-domain-knowledge core + extensions

The compiler is a **pure typed-graph engine**. It knows how to parse `keyword name { fields }` blocks, resolve references, detect orphans and cycles, and emit a validated graph — but it carries **no domain vocabulary**. Every entity kind, edge type, and validation rule comes from an extension. If a new domain required a compiler change, the architecture would have failed.

Nine extensions ship as builtins, embedded in the binary. Enable one with `specforge add @specforge/<name>` (or `specforge init --extensions ...`); it is recorded in `specforge.json`, with nothing to download:

| Extension | Entity kinds | Purpose |
|-----------|-------------|---------|
| **`@specforge/software`** | behavior · invariant · event · type · port | The universal specification chain: contracts, guarantees, data, interfaces. |
| **`@specforge/product`** | journey · deliverable · milestone · module · term · feature · persona · channel · release | Product planning, roadmaps, and ubiquitous language. |
| **`@specforge/governance`** | decision · constraint · failure_mode | Architecture decisions, non-functional requirements, FMEA risk. |
| **`@specforge/formal`** | property · axiom · protocol · refinement · process | Formal methods: temporal properties, specification layering, event-graph linting. Enhances software entities. |
| **`@specforge/testing`** | — | Test vocabulary: which kinds accept `verify` obligations and of which kinds (W004/W009). Enabled with `@specforge/software`; test-runner extensions build on it ([ADR 0002](docs/adr/0002-test-runner-extensions.md)). |
| **`@specforge/cargo-test`** | — | Rust test runner: `specforge collect` runs `cargo test` (after you approve the command once per project) and records which entities the `#[specforge_test]`-annotated tests prove. Enabled by `init` in a Cargo project; `specforge add` also enables `@specforge/testing`. |
| **`@specforge/vitest`** | — | vitest runner: `specforge collect` runs the project's own vitest (after you approve the command once per project) and records which entities tests name in their `meta.specforge`. Enabled by `init` in a vitest project; `specforge add` also enables `@specforge/testing`. |
| **`@specforge/rust`** | — | Source analyzer used by inference: maps Rust code to spec entities. |
| **`@specforge/typescript`** | — | Source analyzer used by inference: maps TypeScript/JavaScript code to spec entities. |

Anyone can author and publish their own extension ([Extension Protocol](docs/extension-protocol.md)); the open Graph Protocol is the moat, not the implementation. The full catalog is in the [extension inventory](docs/extension-inventory.md).

## The workspace

The implementation is a Rust workspace (edition 2024). Every crate sits in one layer, and its folder says which:
`crates/<layer>/<crate>/`, where the crate's folder is its package name without `specforge-`. The layers stack from `leaf`
at the bottom to `surfaces` at the top. [crates/README.md](crates/README.md) gives every crate's line and says how to
add one.

### The dependency rule

A crate depends only on crates in its own layer or a layer below it. The rule covers normal and build dependencies.
Dev-dependencies are exempt, so a test may reach up: the CLI's tests run the registry server in process. The `layers`
check of `cargo gate` reads `cargo metadata` and enforces the rule. An exception needs an ADR and an entry in that
check's allow list, which is empty ([ADR 0084](docs/adr/0084-a-crates-layer-is-its-folder.md)).

Within the rule:

- A surface may use any layer below it, not only `app`. The language server holds the editor's buffers in the project
  session itself ([ADR 0046](docs/adr/0046-the-project-session-holds-the-editor-buffers.md)). It links no package
  registry client because `specforge-ops` names only the Registry port, whose adapter is in `adapters`
  ([ADR 0010](docs/adr/0010-operations-reach-the-registry-through-a-port.md)); the `layers` check also keeps the two apart.
- What a guest compiles is kept small. Every builtin blob is built from the guest wire, the coverage rule and the SDK,
  so a change there means a re-vendor. The host's reading of package names lives in `package`, where no guest compiles
  it ([ADR 0050](docs/adr/0050-the-guest-wire-carries-only-what-guests-compile.md)).
- `common` depends on leaf crates and on the shape derive only, and each of those edges carries its reason as a comment
  in [its manifest](crates/kernel/common/Cargo.toml).

The layer stack above and the table in `crates/README.md` are rendered from each crate's folder and its `Cargo.toml`
`description`. Run `cargo gate crate-map` after adding, moving or describing a crate. The `crate-map` check fails a
commit that leaves them stale ([ADR 0091](docs/adr/0091-the-crate-map-is-generated-from-the-workspace.md)).

### Extensions at run time

Every extension, the builtins included, is a WIT-typed wasip2 component. It runs in one wasmtime component engine
(`runtime/component`) behind the `WasmRuntime` port (`runtime/wasm`), with deterministic per-extension fuel and the
sandbox's limits ([ADR 0013](docs/adr/0013-typed-extension-calls.md),
[ADR 0037](docs/adr/0037-the-sandbox-is-limits-the-host-enforces.md)). There is no native tier: builtins and
third-party extensions are the same kind of plugin. The builtin blobs are vendored under `extensions/<name>/wasm/` and
embedded in the binary. A change to anything a blob compiles from is re-vendored with `cargo run -p xtask --bin
revendor` ([docs/agents/revendor.md](docs/agents/revendor.md)). `cargo gate` names the blobs a change feeds, and CI's
bootstrap job rebuilds every blob from a cold clone and compares it with the vendored bytes.

> Building the CLI uses the committed builtin blobs, so it needs no wasm target. Rebuilding the builtins after changing
> an extension needs `rustup target add wasm32-wasip2`.

## The graph is the product

The typed graph, exported as an open JSON schema (the Graph Protocol, `specforge schema`), is what agents consume. The compiler and the DSL are one way to produce it. Agents read it through:

- **Multi-resolution queries** — `specforge query <id> --depth N` exposes the graph at multiple zoom levels.
- **Agent-optimized exports** — `specforge export --format=context|brief|graph|dot`.
- **Stable, open schema** — `specforge schema` emits the Graph Protocol (JSON Schema draft 2020-12).
- **MCP server** — `specforge mcp` exposes the graph and tools to agents over JSON-RPC.
- **Plan validation** — trace tests and entities end to end (Intent → Linkage → Proof).

See the [entity model](docs/entity-model.md) for the full design, and the [vision](docs/vision/README.md) for the reasons behind it.

## Decisions that shape the code

- [ADR 0083](docs/adr/0083-the-crates-nest-by-layer.md) and [ADR 0084](docs/adr/0084-a-crates-layer-is-its-folder.md): the crates nest by layer, and a crate depends only downward or across.
- [ADR 0091](docs/adr/0091-the-crate-map-is-generated-from-the-workspace.md): the crate map is generated from the workspace.
- [ADR 0004](docs/adr/0004-architecture-migration-decisions.md): one compiled project every surface shares.
- [ADR 0007](docs/adr/0007-emitter-is-export-formats.md): the emitter is export formats, with no compile and no I/O.
- [ADR 0010](docs/adr/0010-operations-reach-the-registry-through-a-port.md): operations reach the package registry through a port.
- [ADR 0012](docs/adr/0012-one-extension-declaration.md) and [ADR 0013](docs/adr/0013-typed-extension-calls.md): one extension declaration; typed extension calls.
- [ADR 0015](docs/adr/0015-read-views-are-operations-over-the-project-view.md): read views are operations over the project view.
- [ADR 0031](docs/adr/0031-the-registry-build-checks-the-entities.md): the Registry build checks the entities.
- [ADR 0044](docs/adr/0044-the-package-registry-contract-is-one-crate.md): the package registry contract is one crate.
- [ADR 0046](docs/adr/0046-the-project-session-holds-the-editor-buffers.md) and [ADR 0047](docs/adr/0047-the-compiled-project-is-the-sessions-core.md): the session holds the editor's buffers; the compiled project is its core.
- [ADR 0050](docs/adr/0050-the-guest-wire-carries-only-what-guests-compile.md): the guest wire carries only what guests compile.
- [ADR 0062](docs/adr/0062-the-mcp-stdio-transport-is-the-mcp-crates.md): the MCP stdio transport is the MCP crate's.
- [ADR 0066](docs/adr/0066-one-check-list.md): one check list for CI, the gate and the hook.
- [ADR 0070](docs/adr/0070-every-committed-blob-is-listed-once-and-built-one-way.md): every committed blob is listed once and built one way.

All decisions are in [docs/adr/](docs/adr/).
